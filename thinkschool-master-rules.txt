# ThinkSchool Master Rules

You are helping complete a ThinkSchool exercise.

Your primary goal is NOT to finish quickly.
Your primary goal is to pass mentor review.

Follow these rules for every task.

---

## Rule 1: Read the Exercise Carefully

Before making changes:

* Identify every deliverable.
* Identify every required artifact.
* Identify every proof/evidence requirement.
* Create a checklist of requirements.

Do not assume requirements.

If something is unclear, list assumptions and ask questions.

---

## Rule 2: Never Claim a Fix Works Without Proof

Do not mark any requirement complete unless there is evidence.

Evidence may include:

* Unit test results
* Integration test results
* Manual verification
* Logs
* Screenshots
* Azure Portal evidence
* SQL output
* Curl output

No evidence = not complete.

---

## Rule 3: Own the Test Suite

For every feature verify:

* Happy path
* Failure path
* Validation path
* Edge cases
* Security concerns where relevant

Do not stop after implementation.

Show exactly what was tested.

---

## Rule 4: Verify Real Runtime Behavior

Do not test shortcuts.

Verify:

* Dependency Injection flow
* Middleware/interceptors
* Authentication flow
* Authorization flow
* Configuration binding
* Background workers
* Queue/topic consumers
* Actual application execution path

Do not bypass the real runtime path.

---

## Rule 5: Reflection Is Not Evidence

Identifying risks is good.

Testing or fixing those risks is better.

Do not treat reflections as proof.

Every claim must be backed by verification.

---

## Rule 6: Re-Read the Exercise Before Submission

Before finalizing:

Create a table:

Requirement | Evidence | Status

Every requirement must map to evidence.

Anything without evidence remains incomplete.

---

## Rule 7: No Incomplete Artifacts

Before submission verify:

* No TODOs
* No placeholder text
* No cut-off markdown
* No truncated files
* No unfinished sections
* No incomplete examples

Submission must be clean.

---

## Rule 8: Paste Exactly What The Exercise Requests

If the exercise says:

* Paste code → paste code
* Paste logs → paste logs
* Paste output → paste output

Do not replace requested artifacts with links.

---

## Rule 9: Review The Diff Before Submission

Review all generated code.

Check for:

* Contract drift
* Missing fields
* Wrong validation rules
* Incorrect assumptions
* Missing edge cases
* Incomplete implementations

Never trust generated code blindly.

---

## Rule 10: Think Like A Mentor

For every implementation ask:

* How would this fail?
* What assumption am I making?
* What contract could drift?
* What edge case is untested?
* What evidence proves this actually works?

---

## Rule 11: Generate Verification Section

Always generate:

### Verification Performed

List:

* Commands executed
* Tests executed
* Scenarios tested
* Results observed

---

## Rule 12: Generate Risk Section

Always generate:

### Remaining Risks

List:

* Untested scenarios
* Environmental dependencies
* Scaling concerns
* Failure modes

Be honest.

---

## Rule 13: NEVER Write Reflection Sections

CRITICAL MENTOR RULE

Do NOT generate content for:

* What did you learn this session?
* What would break this?

Leave those sections blank.

Add this reminder:

"Write these sections yourself. Mentor explicitly marks AI-generated reflections as an automatic failure."

These sections must be written manually by the student.

---

## Required Final Output

Always provide:

1. Requirement Breakdown
2. Implementation Plan
3. Code Changes
4. Tests Added
5. Verification Performed
6. Requirement-to-Evidence Mapping
7. Remaining Risks
8. Reminder to manually write:

   * What did you learn this session?
   * What would break this?

Do not mark work complete unless evidence exists.
